The Rollup layer groups events. Like the Read layer, it never touches the network.

## What a rollup is

`rollup(events, { by, tz? })` returns a sorted `Rollup[]` with summed tokens, events, turns, calls, and `costUsd` (the summed recorded cost, present only when an event carried one). Group along whichever axis your report needs:

- **`tz` buckets days in an IANA timezone on every path.** The TypeScript implementation uses `Intl.DateTimeFormat`. The native core (`skopli-core`) and every facade that calls it (Python, Ruby, Java, C#, Go, Swift, and the C ABI) bucket days in the same zone, DST transitions and sub-hour offsets included, so all SDKs agree bucket for bucket. An unknown zone name falls back to UTC. See the [date and timezone semantics](/skopli/guide/reading/#date-and-timezone-semantics) for how `tz` maps events to day buckets.
- **Workspace bucketing** folds events without a workspace under the `"(unknown)"` sentinel.

## Billing blocks

`by: "block"` groups events into rolling session windows that approximate a provider's usage-quota window, for example Claude subscription five-hour blocks. It is a convenience view of your own recorded usage, not official provider accounting, and will not reproduce a provider's exact quota bookkeeping.

A block opens at the first event's timestamp floored to the hour (in `tz`, or the system timezone when `tz` is omitted) and spans `blockMs` (default five hours, `18000000`). Events in `[start, start + blockMs)` join that block. The first event at or past `start + blockMs` opens a new block, so an idle gap of `blockMs` or longer starts a fresh window. Each row's `key` is the ISO-8601 block-start instant. Events are ordered by timestamp before windowing, and rows come back in ascending start order.

The library never reads the clock, so it does not mark a block active for you. To flag the still-open block, compare its `end` (`start + blockMs`) against the current time caller-side.

## How to price rollups

To turn a rollup into USD, hand it to the Price layer. `priceRollups` prices the tokens already summed onto each rollup, exact for flat-rate models.

See [Pricing basics](/skopli/guide/pricing-basics/) for how matching, cost math, and cost modes work.

## When to use events instead

For tiered (context-sensitive) models, prefer `priceEvents`. It prices each event at its own context before aggregating, so summing several events never pushes the combined context across a tier boundary none of them reached.

See [Rollup pricing vs per-event pricing](/skopli/pricing/rollups-vs-events/) for the full comparison.
