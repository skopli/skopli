Point Skopli at the session logs your coding agents already keep, and turn them into priced usage data. It reads tokens, sessions, turns, and calls from local disk, normalizes them into usage events, and prices those events against market catalogs. You build the dashboards, reports, and billing checks on top.

Skopli is a library, not a service, so there are no accounts and no telemetry. The readers never touch the network. Only the Price layer does: it fetches market catalogs by default the first time you price, caches them on disk, and keeps pricing from that cache when offline (see [Pricing basics](/skopli/guide/pricing-basics)).

Four calls, shown here in TypeScript:

```ts
import { detectHarnesses, readUsage, rollup, createPricing } from "skopli";

const { events } = await readUsage({ since: "2026-08-01" });
const byModel = rollup(events, { by: "model" });
const priced = await createPricing().priceRollups(byModel);
```

The same four calls run in every language. TypeScript, Python, Rust, Ruby, Java, C#, Go, Swift, and C share one Rust core. See [Getting started](/skopli/guide/getting-started) for the quickstart in all nine.

## What you can do

Read, rollup, and price are independent. Use any subset. Events go in, rollups come out, and priced rows come back.

- **Read** parses local session state from 40 harnesses into normalized usage events, with structured diagnostics. See [Reading usage](/skopli/guide/reading).
- **Rollup** groups events by model, day (timezone-aware in every SDK), session, harness, workspace, or billing block. See [Rollups](/skopli/guide/rollups).
- **Price** matches models against OpenRouter, LiteLLM, and models.dev catalogs (or your own) and computes USD costs. An unmatched model returns `priced: false` with the sources it tried. See [Pricing basics](/skopli/guide/pricing-basics).

## What every event looks like

Every event carries the same fields before any layer touches it:

- `harness`, `timestamp`, `sessionId`, `messageId`, `turn`, `subagent`, `model`
- `tokens`: `input`, `output`, `cacheRead`, `cacheWrite`, optional `cacheWrite1h`, `reasoning`
- `calls`, optional `costUsd` (only when the source reports one), optional `workspace`, optional `title`

`cacheWrite1h` is a portion of the `cacheWrite` total, not additive. Readers subtract reasoning-inclusive output at the source, so nothing bills twice. See [Reading usage](/skopli/guide/reading#event-fields) for the full field semantics.

## When to use Skopli

- Your agents run on machines you control and keep local session logs.
- You want usage and cost across many harnesses in one pipeline.
- You need offline reads, timezone-aware day rollups, or cache-write split pricing.
- You want misses reported as misses, not guesses.

## When not to use Skopli

- Your tool keeps token data cloud-side only (vendor dashboard, quota APIs, no local token file). See [Coverage](/skopli/reference/coverage) for the per-tool reasons.
- You only need one vendor's billed total and already trust its dashboard.
- You want a hosted tracker with accounts and telemetry. Skopli is a library, and the read path has no network.

## Diagnosing broken files

The SDK never writes to stdio. Problems come back as structured diagnostics alongside your data:

```ts
const { events, diagnostics } = await readUsage();
for (const d of diagnostics) {
  // { severity: "warning" | "info", message, harness?, path? }
  console.warn(d.severity, d.message, d.path ?? "");
}
```

Each diagnostic names its severity, what went wrong, and (when known) which harness and file it came from. Re-check the path, re-run for that harness, or ship the diagnostics with the report. Skipped source files arrive per harness in `skipped`. See [Diagnostics and error shapes](/skopli/reference/api#diagnostics-and-error-shapes) for the full field table.
